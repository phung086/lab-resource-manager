## D. Booking-State Transformation

The canonical physical lifecycle is:

`PENDING_APPROVAL`, `CONFIRMED`, `CHECKED_OUT`, `RETURNED`, `COMPLETED`, `REJECTED`, `CANCELLED`.

The migration locks `bookings`, verifies the legacy enum and ranges, removes the old guard inside the same transaction, replaces the enum through an explicit `CASE`, then recreates the guard before commit. Mapping is `pending -> PENDING_APPROVAL`, `approved -> CONFIRMED`, `checked_out -> CHECKED_OUT`, and direct uppercase equivalents for completed/rejected/cancelled. Payment is not a booking state.

Added nullable evidence fields are `approvedAt`, `returnedAt`, `completedAt`, `outcome`, and `outcomeAt`. Historical timestamps remain null because no trustworthy source exists.

## E. no_show Policy

Verified evidence is zero booking `no_show` rows, zero `NO_SHOW` behavior events, and zero users with `noShowCount > 0`. The migration nevertheless rechecks booking rows and aborts if the count is nonzero.

Batch 1D found that an exception raised inside the explicit transaction was obscured by Prisma's later transaction-aborted error. The final migration therefore repeats the loss-prevention `no_show` count as a read-only preflight before `BEGIN`; a nonzero count now surfaces the actionable `P0001` message before any schema or data mutation. The guarded transactional check remains as defense in depth.

`NO_SHOW` is a terminal outcome/event, not a reserving state. A future authorized service transaction must:

1. Move a still-confirmed booking to `CANCELLED` under an approved no-show policy.
2. Set `Booking.outcome=NO_SHOW` and `outcomeAt` to the real detection time.
3. Append `UsageLog.action=NO_SHOW` with `fromStatus`, `toStatus`, actor type/ref, reason and metadata.

No historical actor, timestamp or reason is fabricated by this migration.

## F. Booking Guard Replacement

The canonical constraint is `bookings_no_active_overlap`:

```sql
EXCLUDE USING gist (
  "resourceId" WITH =,
  tsrange("startAt", "endAt", '[)') WITH &&
)
WHERE (status IN ('PENDING_APPROVAL','CONFIRMED','CHECKED_OUT','RETURNED'))
```

`btree_gist` is required before 1C. `bookings_valid_time_range` enforces `startAt < endAt`. PostgreSQL emits SQLSTATE `23P01`; a later runtime batch must map it deterministically to `BOOKING_CONFLICT`.

## G. Maintenance Concurrency Strategy

Evaluated designs:

| Option | Decision |
|---|---|
| Resource-row lock | **Selected**: smallest design tied to the existing resource aggregate |
| Unified blocking table | Rejected for now: strongest single-table model but rewrites booking/maintenance persistence |
| Advisory lock | Rejected: protocol is easier to bypass and lock-key governance adds hidden complexity |

The selected protocol is enforced centrally by `enforce_resource_schedule_integrity()` triggers, not only by application convention. Every active booking or maintenance insert/update first locks the corresponding `resources` row with `FOR UPDATE`, then checks the other table. Conflicts raise `23P01`. GiST remains the booking-vs-booking authority. Active maintenance means `scheduled` or `in_progress`.

Scheduling writes use PostgreSQL `READ COMMITTED`, the Prisma/PostgreSQL default, so the check after a waited row lock receives a fresh statement snapshot. The trigger rejects scheduling writes under a different isolation level with SQLSTATE `25000`; this prevents an untested stale-snapshot path from committing. Batch 1D must prove the wait/check sequence with separate connections.

This guarantees booking/booking, booking/maintenance, maintenance/booking, and maintenance/maintenance serialization for a resource. Multi-resource operations must acquire resource locks in sorted ID order in later application code.

## I. Operational-Status Cutover

`Resource.operationalStatus` is authoritative. Scheduling availability is derived from operational state, booking range, maintenance range and policy. `RESERVED` is never an operational state.

The migration rejects legacy `status=reserved`, normalizes physical `OperationalStatus` labels to uppercase, and performs one compatibility backfill from authority to `Resource.status`. The compatibility projection is:

- `AVAILABLE -> available`
- `IN_USE -> in_use`
- `MAINTENANCE`, `CALIBRATION`, `BROKEN -> maintenance`
- `RETIRED`, `OFFLINE -> offline`

The known `UAV-M350-RTK-01` disagreement is corrected from `AVAILABLE` to `MAINTENANCE` only when its exact verified precondition is present. A deterministic migration-owned status-history row records the actual reconciliation time and reason with null actor; it does not claim a historical human action. Any other disagreement aborts.

The compatibility column remains in 1C. Later runtime work must make one authorized operational-status writer maintain the projection transactionally, migrate all readers, reject direct compatibility writes, and remove the field only in a separately approved migration.

## J. Lifecycle and Audit Additions

Existing `UsageLog` is extended as the canonical booking-linked transition history. Added fields are `actorType`, `actorRef`, `fromStatus`, `toStatus`, `reason`, and JSON `metadata`. Existing `userId` becomes nullable so system/service actors do not require a fake user. A CHECK requires either a real user actor or a non-empty system/service reference.

`UsageAction` is physically normalized to uppercase and adds `RETURN`, `COMPLETE`, and `NO_SHOW`; existing check-in and telemetry events remain. Existing `conditionBefore` and `conditionAfter` continue to hold before/after-use evidence. No duplicate history model is created.

IDs remain text for compatibility. The frozen convention is application-generated UUID v4 for new core entity IDs; existing IDs remain valid and no database ID default is introduced. `createdAt` uses database `CURRENT_TIMESTAMP`; Prisma `@updatedAt` owns normal update timestamps. Existing `timestamp(3) without time zone` columns are retained and interpreted as UTC by contract.

## K. Audit Retention

Critical resource/history FKs change from `CASCADE` to `RESTRICT` for bookings, usage logs, maintenance windows, incidents, status history and telemetry. Resources are retired with `OperationalStatus.RETIRED`, not normally hard-deleted. Bookings are cancelled/rejected/completed, not hard-deleted.

Configuration-owned cascades such as capability, requirement and nested document rows remain unchanged. Optional advanced allocations also remain unchanged. Account hard-delete policy and remaining cascades require a later authorization/archival batch; 1C does not rewrite every FK without evidence.

## P. Rollback and Restore

Before commit, any SQL error rolls back the complete 1C transaction, including enum replacement, FK replacement, triggers and data corrections. There is no reverse migration because reversing lifecycle labels/outcomes would be unsafe.

Controlled destructive DDL is limited to dropping and recreating the old booking guard, replacing the legacy `BookingStatus` and `UsageAction` enum type objects after guarded row conversion, replacing the seven-label `ResourceType` only on the enforced-empty clean path, and replacing seven FK constraints with `RESTRICT` equivalents. No table, column, valid application row, advanced module, or historical migration is deleted.

After a successful isolated test migration, rollback means discarding that test database and restoring the verified dump into a new database. Eventual source rollback, if separately approved, also uses the verified custom-format dump and row-count manifest. Never overwrite the source volume during 1D.
